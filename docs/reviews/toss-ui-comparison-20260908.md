**LorePia UI 비교 분석 · 2026-09-08**

현재 Tauri 앱, 공유 UI 소스, 브라우저 목업, 사용자가 제공한 토스 스크린샷 12장을 비교했다. 이번 작업은 분석이며 앱 소스와 설정은 변경하지 않았다. 브라우저의 임시 화면 크기는 측정 후 원래대로 복원했다.

**참고 범위**

[앱인토스 UI/UX 가이드](https://developers-apps-in-toss.toss.im/design/consumer-ux-guide)는 미니앱 입점 규격과 일반적인 사용성 원칙이 함께 있는 문서다. 예측 가능한 이동, 결과가 명확한 버튼 문구, 논리 좌표와 이미지 픽셀의 구분을 LorePia에 적용할 수 있다. 게임 풀스크린 설명이나 입점용 탭바 규격을 일반 채팅 앱의 의무 규격으로 해석하지 않는다.

아래 치수는 LorePia의 CSS px 실측이다. 첨부 JPEG의 픽셀 수는 기기의 논리 해상도, 배율, 글자 크기 설정을 알려주지 않는다. 특히 기존 618×1280 이미지와 새로운 591×1280 이미지에는 상태 표시줄의 포함 여부도 다르므로, 스크린샷 위쪽 끝을 그대로 같은 좌표로 간주하면 안 된다.

**1. 글자가 그대로 남는 현상은 실제 구현과 일치한다**

[responsive-layout.ts](/Users/codexer/lorepia/apps/lorepia/src/ui/workspace/responsive-layout.ts:20)는 `scale = 1`을 반환한다. 전체 화면이 동일 비율로 축소되는 구조가 아니다. `WorkspaceFrame`에는 축소 transform 분기가 남아 있지만 현재 계산에서는 사용되지 않는다.

높이 852px, 기본 글자 크기에서 측정한 결과:

| 화면 폭 | 캐릭터 제목 | 기본 본문 | 상단 SVG 박스 | 버튼 터치 영역 | 캐릭터 열 폭 |
| --- | --- | --- | --- | --- | --- |
| 320px | 22px | 17px | 28×28px | 48×48px | 64px |
| 360px | 22px | 17px | 28×28px | 48×48px | 72px |
| 393px | 22px | 17px | 28×28px | 48×48px | 72px |
| 430px | 22px | 17px | 28×28px | 48×48px | 72px |

320px 폭에서 높이를 852→552px로 바꾸면 배너 높이는 112→약 77.27px로 줄고, 제목과 버튼 크기는 그대로다. 배너가 [ui-layout.css](/Users/codexer/lorepia/apps/lorepia/src/ui/workspace/ui-layout.css:185)의 `clamp(72px, 14dvh, 112px)`를 사용하기 때문이다.

따라서 작은 화면에서 이미지·빈 공간·사용 가능한 가로폭은 줄고 글자와 조작부의 존재감은 상대적으로 커진다. 글자 하나의 문제가 아니라 서로 다른 크기 계산 규칙을 함께 쓰는 문제다. 359px 이하에서는 일부 여백과 캐릭터 열만 줄이는 별도 규칙도 있다.

창 크기 변경, 화면 전체의 축소, 사용자의 큰 글자 설정은 구분해야 한다. 좁은 창에 맞춘 시각적 축소를 도입하더라도 읽기 크기와 터치 영역의 하한을 정하고, 사용자가 선택한 글자 크기를 다시 상쇄하지 않아야 한다. 일반적인 휴대폰 폭에서 글자가 일정한 것 자체가 잘못은 아니다.

**2. 뒤로가기와 앱 설정의 가로 중심이 다르다**

393px 폭의 콘텐츠 영역을 기준으로:

| 대상 | 버튼 왼쪽 | 버튼 중심 X | 버튼 중심 Y | SVG 박스 |
| --- | --- | --- | --- | --- |
| 캐릭터 열 맨 위 앱 설정 | 12px | 36px | 30px | 28×28px |
| 설정 페이지 뒤로가기 | 4px | 28px | 30px | 28×28px |

세로 높이와 버튼 크기는 같다. 가로로 8px 차이가 난다. 320px에서는 캐릭터 열이 64px이 되어 앱 설정 중심이 32px으로 이동하지만 뒤로가기는 28px이어서 차이가 4px으로 바뀐다.

원인은 앱 설정을 캐릭터 열 중앙에 놓고, 뒤로가기는 별도의 화면 여백에 배치한 것이다. 의도적인 시각 보정이라는 근거는 없으며 두 레이아웃 규칙이 연결되지 않은 상태다. 근거: [내비게이션 여백](/Users/codexer/lorepia/apps/lorepia/src/ui/workspace/ui-layout.css:49), [캐릭터 열과 설정 배치](/Users/codexer/lorepia/apps/lorepia/src/ui/workspace/ui-layout.css:108), [좁은 화면 예외](/Users/codexer/lorepia/apps/lorepia/src/ui/workspace/ui-feedback.css:245).

추천은 캐릭터 열의 중심축을 상단 내비게이션과 공유하는 것이다. 현재 72px 열을 유지한다면 48px 버튼의 양옆 여백은 12px, 64px 열에서는 8px이 된다. 뒤로가기만 이동하는 데서 끝내지 말고 반대편 상단 버튼, 제목과의 간격도 같은 규격에 맞춘다. 본문 전체를 버튼의 바깥선에 맞춰 이동할 필요는 없다. 본문 시작선과 아이콘 중심선은 역할이 다르다.

캐릭터 이름 옆의 **카드 설정**은 앱 설정과 별개다. 캐릭터 정보에 속하므로 본문에 있는 것이 자연스럽다. 모든 톱니바퀴를 같은 상단 위치로 옮기면 적용 범위를 구별하기 어려워진다.

[TDS Navbar](https://tossmini-docs.toss.im/tds-react-native/components/navbar/)도 왼쪽 이동, 가운데 제목, 오른쪽 동작을 하나의 내비게이션 구성으로 다룬다. 이 구조를 참고하되 캐릭터 열을 포함한 LorePia의 세 화면 구성은 유지할 수 있다.

**3. 글자 크기 목록보다 역할 배정이 부족하다**

[TDS Typography](https://tossmini-docs.toss.im/tds-react-native/foundation/typography/)의 기본 토큰에는 제목 26/35·22/31, 작은 제목 20/29, 본문 17/25.5, 작은 본문 15/22.5, 보조 텍스트 13/19.5가 있다. 숫자는 글자 크기/줄 높이다. 토큰으로 위계를 관리하고 큰 글자 설정에 대응한다.

LorePia도 22·20·17·15·13px과 비슷한 줄 높이를 이미 사용한다. 현재 어색함을 전부 글자 크기 오류로 볼 수는 없다. 다만 페이지 제목 22px/600과 그룹 제목 20px/600이 비슷한 무게를 가져, 페이지의 중심이 약하게 보인다. 근거: [제목과 카드 그룹](/Users/codexer/lorepia/apps/lorepia/src/ui/workspace/ui-content.css:61), [그룹 제목](/Users/codexer/lorepia/apps/lorepia/src/ui/workspace/ui-content.css:149).

다음은 토스의 강제 규격이 아니라 LorePia에 대한 제안이다.

| 역할 | 제안 |
| --- | --- |
| 독립된 페이지의 큰 제목 | 26px, 줄 높이 35px |
| 좁은 상세 화면 제목 | 22px, 줄 높이 31px |
| 일반 설정 그룹 제목 | 17~18px, 굵기로 구분 |
| 목록의 주된 문구·대화 본문 | 17px, 줄 높이 25.5px |
| 설명·현재 설정값 | 15px, 줄 높이 22.5px |
| 날짜 등 우선순위가 낮은 정보 | 13px, 줄 높이 19.5px |
| 상단 조작부 | 같은 크기의 SVG 박스와 48px 터치 영역 |

전송, 내비게이션, 목록 화살표까지 모두 같은 크기로 만들기보다는 각 역할 안에서 일관되게 맞춘다.

**5. 함께 발견한 사용성 문제**

- AI 설정의 ‘중단된 응답 보존’은 켜기/끄기 선택인데 큰 선택 시트를 거친다. 첨부 11번처럼 행 안의 스위치로 표현하면 상태를 보고 바로 바꾸기 쉽다. 값은 기존 저장 정책에 따라 초안으로 유지하면 된다.
- 같은 값을 다시 선택해도 `dirty = true`가 된다. 실제 변경이 없어도 돌아갈 때 ‘수정 중’ 확인창이 뜰 수 있다. [WorkspaceAiSettings.svelte](/Users/codexer/lorepia/apps/lorepia/src/app/workspace/ai/WorkspaceAiSettings.svelte:126)의 현재 동작이다. 저장 전후 값의 차이로 확인창 필요 여부를 판단하는 편이 맞다.
- 같은 AI 화면에서 저장과 요청 구조 미리보기에 모두 주된 버튼 표현을 사용한다. 미리보기처럼 부가적인 행동의 강조를 낮추면 무엇을 먼저 할지 명확해진다.
- 연결 첫 화면에서 카탈로그·동기화·모델 기능 등 고급 기능까지 함께 드러난다. 기본 연결 및 모델 선택을 먼저 제시하고 고급 관리로 묶을 여지가 있다.

확인창은 실제 작업 손실을 알려줄 때 필요하다. 값이 그대로인데 이동을 막는 동작은 예측 가능한 이동을 강조하는 [가이드의 방향](https://developers-apps-in-toss.toss.im/design/consumer-ux-guide)과 맞지 않는다는 분석이다. 보존·버리기 버튼은 이미 사용자가 정한 오른쪽 메인색/왼쪽 회색 원칙을 유지한다.

**수정 순서 제안**

1. 캐릭터 열·뒤로가기·상단 반대편 버튼의 중심축과 간격을 공통 규격으로 정한다.
2. 기준 모바일 폭과 좁은 창의 축소 하한을 정한다. 이미지·여백·글자에 어떤 값이 함께 적용될지 명시하고 큰 글자 설정은 독립적으로 유지한다. 큰 창에서는 내용 영역과 열 배치를 확장한다.
3. 페이지 제목, 그룹 제목, 본문, 보조 정보의 역할을 나누고 같은 역할에 같은 토큰을 적용한다.
4. 단순 상태 변경에 필요한 단계를 줄이고 실제 변경이 있을 때만 이탈 확인을 표시한다.
5. 같은 내용으로 320·360·393·430px, 낮은 창, PC 열 전환을 다시 확인한다. 스크린샷의 물리 픽셀이나 특정 휴대폰의 종횡비를 강제로 고정하지 않는다.

UI 구현 수정이나 재빌드는 수행하지 않았다. 비교에 사용한 브라우저 목업은 공유 UI 컴포넌트를 사용하며, Tauri 앱의 실제 데이터와 설정 화면도 별도로 확인했다.
